2.	What is Inheritance?
  Inheritance is a concept in which one object acquires/inherits another object’s properties. Inheritance represents the parent-child relationship.

4.	What is Polymorphism?
Polymorphism refers to many forms, or it is a process that performs a single action in different ways.
Polymorphism is of two different types
 Compile time polymorphism: When we overload a static method in java.
 Run time polymorphism: It is also called a dynamic method dispatch is a method in which a call to an overridden method is resolved at run time rather than compile time. In this method, the overridden method is always called through the reference variable.
By using method overloading and method overriding, we can perform polymorphism.
5.	What is Encapsulation?
Encapsulation is the process that binds together the data and code into a single unit and keeps both from being safe from outside interference and misuse.

 In this process, the data is hidden from other classes and can be accessed only through the current class’s methods. Hence, it is also known as data hiding.

Encapsulation acts as a protective wrapper that prevents the code and data from being accessed by outsiders. These are controlled through a well-defined interface.

Encapsulation is achieved by declaring the variables as private and providing public setter and getter methods to modify and view the variable values.

14.	What is SerialVersionID?
Serialization at the time of serialization, with every object sender side JVM will save a Unique Identifier. JVM is responsible to generate that unique ID based on the corresponding .class file which is present in the sender system.
Deserialization at the time of deserialization, receiver side JVM will compare the unique ID associated with the Object with local class Unique ID i.e. JVM will also create a Unique ID based on the corresponding .class file which is present in the receiver system.
 If both unique ID matched then only deserialization will be performed. Otherwise, we will get Runtime Exception saying InvalidClassException. This unique Identifier is nothing but SerialVersionUID.

18.	PermGen space vs Meta space?
PermGen stands for Permanent Generation. It is a special type of heap space. It is separate from the main memory (heap). JVM uses PermGen to keep track of loaded class metadata. All the static content is stored by the JVM
to this memory section. Static content can be a static method, references to the static object and primitive variables. PermGen also contains information about bytecode, names, and JIT.
Metaspace is a new memory space – starting from the Java 8 version; it has replaced the older PermGen memory space. The most significant difference is how it handles memory allocation.
•	Specifically, this native memory region grows automatically by default.
•	The garbage collection process also gains some benefits from this change. The garbage collector now automatically triggers the cleaning of the dead classes once the class metadata usage reaches its maximum metaspace size.
Therefore, with this improvement, JVM reduces the chance to get the OutOfMemory error

42.	What is the need of ConcurrentHashMap and how it is different from HashMap?
•	In case of normal hashMap or synchronized hashmap, whenever we are accessing an element it will lock other buckets as well along with current accessing one. But in case of ConcurentHashMap this locking is limited to segment wise that means only that particular bucket will be locked.
•	The HashMap is non-thread-safe and cannot be used in a Concurrent multi-threaded environment. Comparatively, ConcurrentHashMap is a thread-safe and specially designed for use in multi-threaded and concurrent environment.
•	HashMap is faster in single threaded environment whereas ConcurentHashMap is slightly better in multi-threaded environments.
•	HashMap allows storing of null keys/values whereas ConcurentHashMap won’t allow nulls as keys/values,
•	HashMap – FailFast , ConcurentHashMap – FailSafe

So, For HashTable At a time only one thread is allowed to do modification but inc case of ConcurentHashMap multiple threads are allowed to do modifications.

45.	How HashMap Internally works?
•	When we create HashMap it will create an empty 16 buckets (0-15) where every bucket considered as LinkedList. Each bucket contains multiple Nodes.
•	When we try to put a value in hashMap , put method internally calls hash method which will evaluate hashvalue for given key. Based on hashValue index value is calculated.
•	Map.put(e1,”Dev”); //Let’s assume we got 6 as index. So it’s added to 6th index bucket.
•	Map.put(e2,”QA”); //Let’s assume we got 9 as index. So it’s added to 9th index bucket.
•	Map.put(e3,”UI”); //Let’s assume we got 6 as index. But we have already object present at obtained bucket. This is called hashing Collision. After this , it checks equals method to check if both the content are same or not. If it find different it will add it to same bucket node. If it is same it will replace with new object.
•	If key is null, Entry will be based in 0 bucket.
46.	What is the enhancement done for HashMap in Java8?
If for the same node, hash Collisions occurs more than 5 then it converts LinkedList to BalancedTree to maintain balance of nodes.

57.	JVM Memory:

CSRF:
Cross-Site Request Forgery (CSRF) is a type of attack that tricks the victim into submitting a malicious request usually to change state of resources. It uses the identity and privileges of the victim to perform an undesired function on their behalf.  For most sites, browser requests automatically include any credentials associated with the site, such as the user's session cookie, IP address, etc. Therefore, if the user is authenticated to the site, the site cannot distinguish between legitimate requests and forged requests.
 By default, Spring Security's CSRF protection produces a unique token for each session. This token must be included in PATCH, POST, PUT, and DELETE methods. The server will then validate the token before processing the request. If the token is missing or invalid, the server will reject the request.
Stateless APIs: If you are building a stateless REST API that does not use sessions or cookies for authentication (e.g., using token-based authentication like JWT), CSRF protection may not be necessary. In such cases, the API relies on tokens passed in headers, which are not vulnerable to CSRF attacks.

@PreAuthorize and @Secured. Explain Uses and corresponding use cases:
`@PreAuthorize` and `@Secured` are annotations provided by Spring Security to enforce method-level security in a Spring application. They are used to specify access control rules for methods, allowing you to define who can invoke a particular method based on roles or expressions.
`@PreAuthorize` is used to specify a SpEL (Spring Expression Language) expression that determines whether a method can be invoked. It is more flexible and powerful than `@Secured` because it allows for complex expressions and conditions.
•	Role-Based Access Control :You can use `@PreAuthorize` to restrict access to methods based on user roles.
    	@PreAuthorize("hasRole('ADMIN')")
    	public void adminOnlyMethod() {
       	 // method logic
    	}
•	Permission-Based Access Control**: You can check for specific permissions or authorities.
    	@PreAuthorize("hasAuthority('PERMISSION_READ')")
    	public void readPermissionMethod() {
      	  // method logic
   	 }
•	Complex Conditions**: You can use complex expressions to evaluate conditions based on method parameters or user attributes.
    	@PreAuthorize("#userId == authentication.principal.id")
    	public void userSpecificMethod(Long userId) {
     	   // method logic
 	   }
`@Secured` is used to specify a list of roles that are allowed to invoke a method. It is simpler and less flexible than `@PreAuthorize` because it only supports role-based access control.
    @Secured({"ROLE_ADMIN", "ROLE_USER"})
    public void adminOrUserMethod() {
        // method logic
    }
- Use `@PreAuthorize` when you need more flexibility and the ability to use complex expressions for access control. It is suitable for scenarios where you need to evaluate conditions based on method parameters, user attributes, or custom logic.
- Use `@Secured` for simple role-based access control where you only need to specify a list of roles. It is easier to use and understand for straightforward role checks.

Hashing of Passwords:
Hashing is a process that transforms a given input (such as a password) into a fixed-size string of characters, which is typically a hexadecimal number. The output, known as the hash, is unique to each unique input. Hashing provides security for passwords in the following ways:
•	Irreversibility: Hash functions are designed to be one-way functions, meaning that it is computationally infeasible to reverse the process and obtain the original input from the hash. This ensures that even if an attacker gains access to the hashed passwords, they cannot easily determine the original passwords.
•	Deterministic: The same input will always produce the same hash output. This allows the system to verify passwords by comparing the hash of the input password with the stored hash.
              Salting: Salting is a technique used to enhance the security of hashed passwords by adding a unique, random value (called a salt) to each password before hashing. This ensures that even if two users have the same password, their hashed passwords will be different
•	Generate a Salt: For each password, generate a unique, random salt. The salt should be long enough to ensure uniqueness and randomness.
•	Combine Password and Salt: Concatenate the salt with the password. This combined value is then hashed.
•	Store the Salt and Hash: Store the salt and the resulting hash in the database. The salt is stored in plaintext alongside the hash.
•	Verify Password: To verify a password, retrieve the stored salt and hash from the database. Concatenate the salt with the input password, hash the combined value, and compare the result with the stored hash. If they match, the password is correct.

### Spring Security Filter Chain
Spring Security uses a filter chain to apply security measures to incoming HTTP requests. The filter chain is a sequence of filters that process requests and responses, providing various security functionalities such as authentication, authorization, CSRF protection, and more.

The filter chain is typically composed of several predefined filters, including:
- `SecurityContextPersistenceFilter`: Manages the `SecurityContext` for the duration of the request.
- `LogoutFilter`: Handles logout requests.
- `UsernamePasswordAuthenticationFilter`: Processes authentication requests using username and password.
- `BasicAuthenticationFilter`: Processes HTTP Basic authentication.
- `CsrfFilter`: Provides CSRF protection.
- `ExceptionTranslationFilter`: Translates exceptions into HTTP responses.
- `FilterSecurityInterceptor`: Performs authorization checks.
To add a custom filter to the Spring Security filter chain, you need to extend the `WebSecurityConfigurerAdapter` and configure the filter chain using the `HttpSecurity` object. You can add your custom filter at a specific position in the filter chain or after/before a specific existing filter.
•	Implement your custom filter by extending `GenericFilterBean` or another appropriate filter class.
    public class CustomFilter extends GenericFilterBean {
        @Override
        public void doFilter(
                HttpServletRequest request,
                HttpServletResponse response,
                FilterChain chain) throws IOException, ServletException {
            // Custom filter logic
            System.out.println("Custom filter executed");
            chain.doFilter(request, response);
        }

        @Override
        public void init(FilterConfig filterConfig) throws ServletException {
            // Initialization logic if needed
        }

        @Override
        public void destroy() {      // Cleanup logic if needed
        }
    }
•	Extend `WebSecurityConfigurerAdapter` and add your custom filter to the filter chain.
    @EnableWebSecurity
    public class SecurityConfig extends WebSecurityConfigurerAdapter {
        @Override
        protected void configure(HttpSecurity http) throws Exception {
            http
                .addFilterBefore(new CustomFilter(), UsernamePasswordAuthenticationFilter.class)
                .authorizeRequests()
                .anyRequest().authenticated()
                .and()
                .formLogin()
          .and()
                .httpBasic();
        }
    }
In the above example, the custom filter is added before the `UsernamePasswordAuthenticationFilter`. You can also use `addFilterAfter` or `addFilterAt` to place the filter at different positions in the filter chain.

OAuth – Core Concept
•	OAuth is for authorization, not authentication.
•	Enables one service to access another service's resources on behalf of a user.
________________________________________
📦 Original Use Case
•	Created to allow service-to-service access (e.g., a printing app accessing a user's photos from Google Drive).
•	Not originally designed for logging users in.
________________________________________
❌ The Credential Problem
•	Asking users for their Google ID and password is insecure.
•	Users don’t want to give full access—just limited permissions (e.g., photos, not email).
________________________________________
💡 Why Sharing Links Doesn’t Work
•	Not all data/services support sharing (e.g., address books).
•	Sharing is not always practical or secure.
________________________________________
🔑 Valet Key Analogy
•	OAuth is like a valet key: it starts the car but doesn’t open the trunk.
•	Users grant limited, scoped access to third-party services.
________________________________________
🌐 OAuth as a Standard
•	OAuth 2.0 is the current widely used version.
•	It's an open standard with a defined flow for interoperability.
________________________________________
🔁 OAuth Flow (Simplified)
1.	Service requests access to user’s data from a provider (e.g., Google).
2.	Provider asks the user for permission.
3.	If granted, the provider issues an authorization token.
4.	Service uses the token to access permitted resources.
________________________________________
🪪 Access Tokens & JWT
•	Tokens represent granted permissions.
•	Usually implemented as JWTs (secure, self-contained tokens).
•	Only the provider (e.g., Google) can issue valid tokens.
________________________________________
🚫 OAuth ≠ Authentication
•	Users are already logged in (authenticated).
•	OAuth manages what services are allowed to do on behalf of the user.


OAuth Terminologies
1.	Resource:
o	A resource refers to the protected data or service being accessed.
o	Example: Photos on Google Drive are the resource that the photo printing service wants to access.
2.	Resource Owner:
o	The user who owns the resource can grant or deny access to it.
o	Example: The user with photos on Google Drive who grants the photo printing service permission to access them.
3.	Resource Server:
o	The server that holds the protected resource.
o	Example: Google Drive, which hosts photos.
4.	Client:
o	The application requests access to the protected resource on behalf of the resource owner.
o	Example: The photo printing service that wants to retrieve photos from Google Drive.
5.	Authorization Server:
o	The server that authenticates the resource owner and issues access tokens to the client.
o	The resource server and authorization server may be part of the same system or separate entities.
________________________________________
Key OAuth Flows
1. Authorization Code Flow (Secure Flow)
•	Steps:
1.	The user logs into the photo printing service and requests access to their photos on Google Drive.
2.	The photo printing service (client) requests access from the authorization server.
3.	The authorization server verifies the request with the resource owner (the user).
4.	Once approved, the authorization server issues an authorization code (short lived) to the client.
5.	The client exchanges the authorization code for an access token with Authorization server.
6.	The client uses the access token to access the protected resource (photos) on the resource server (Google Drive).
By sending an authorization code first (which is a short-lived and intermediate token), the client can securely exchange it for an access token over a backchannel (server-to-server communication) where it's less likely to be intercepted as even if someone intercepts the authorization code, it cannot be used without the client secret
•	Why it’s secure:
o	The access token is securely exchanged after the client receives an authorization code, minimizing the risk of token interception.
2. Implicit Flow (Simplified Flow)
•	Steps:
1.	The user requests access to their photos on Google Drive via the photo printing service.
2.	The photo printing service (client) requests access from the authorization server.
3.	The authorization server checks with the resource owner for approval.
4.	Instead of issuing an authorization code, the authorization server directly sends the access token to the client.
5.	The client uses the access token to access the resource on the resource server.
•	Drawback:
o	The access token is exposed to the browser, which makes it less secure compared to the authorization code flow.
o	Use case: Primarily used for JavaScript applications running in browsers, where the secure storage of tokens is challenging.
3. Client Credentials Flow (Service-to-Service Authorization)
•	Steps:
1.	The client (e.g., microservice) authenticates directly with the authorization server using its own credentials.
2.	The authorization server issues an access token to the client.
3.	The client uses the access token to access the resource server (another microservice) and obtain data.
•	Use case:
o	Ideal for trusted services (e.g., microservices) that need to communicate with each other and access protected resources on behalf of their own systems rather than individual users.
________________________________________
OAuth Concepts in Practice
•	Authorization vs. Authentication:
o	OAuth is designed for authorization (granting access to resources), not authentication (verifying identity).
o	The misconception arises when services offer "Sign in with Google" or "Sign in with Facebook," as these are essentially using OAuth for authorization, not authentication.
•	Security Responsibility:
o	The resource server (e.g., Google Drive) has the responsibility of ensuring secure access to its resources. It needs to validate the access tokens issued by the authorization server.
•	Token Security:
o	In the authorization code flow, access tokens are exchanged securely, while in the implicit flow, the access token is sent directly to the client, posing a potential security risk.
•	When to Use Each Flow:
o	Authorization Code Flow: Best for secure, server-side applications.
o	Implicit Flow: Suitable for client-side JavaScript applications.
o	Client Credentials Flow: Best for communication between trusted services or microservices.

Overview of JWT (JSON Web Token)
•	JWT is a popular method for user authorization in web applications and microservices.
•	It follows the open industry standard RFC 7519, defining how JWTs should be structured and used to exchange information securely.
________________________________________
HTTP and Stateless Protocol
•	HTTP is a stateless protocol, meaning each request must contain all the necessary information for the server to respond.
•	Dynamic web applications require users to be identified in multiple interactions. However, HTTP doesn't inherently remember previous requests.
________________________________________
Session-Based Authentication (Traditional Approach)
•	Session tokens are often used for maintaining user authentication over multiple requests.
•	When a user authenticates, the server creates a session and provides a session ID, which is stored typically in a cookie.
•	In subsequent requests, the browser automatically sends the session ID, allowing the server to identify the user.
________________________________________
Problems with Session Tokens
1.	Distributed Architecture:
o	In modern applications with multiple servers or microservices, the server storing the session information might be different from the one handling a user’s request.
o	This can create session synchronization issues, where each server may not have access to the session data of the other server.
2.	Solutions and Challenges:
o	Shared session caches (e.g., Redis) can resolve this but add complexity.
o	Sticky sessions (where the load balancer directs requests from a particular user to the same server) also limit scalability.
________________________________________
Introducing JWT: A Stateless Solution
•	With JWT, instead of saving session information on the server, the server returns the user information as a token (JWT).
•	This token is a self-contained JSON object containing the user's information (e.g., ID, roles).
•	JWTs are signed to ensure their integrity, meaning the server can trust the data without needing to store anything on its side.
________________________________________
How JWT Works
•	JWT includes three main parts:
1.	Header: Contains metadata such as the algorithm used to sign the token.
2.	Payload: Contains the claims (user data) such as user ID or roles.
3.	Signature: Verifies the authenticity and integrity of the token.
•	The signature ensures that if the token is tampered with, it becomes invalid.
________________________________________
Advantages of JWT
1.	Stateless: No session storage needed on the server, making JWT ideal for distributed architectures.
2.	Scalable: Works well in microservices and load-balanced environments where multiple servers handle requests.
3.	Self-contained: The token itself contains all the information, meaning no server-side session management is required.
________________________________________
JWT vs Session Tokens
•	Session Tokens: Serve as references to server-stored session data.
•	JWTs: Contain the actual information inside the token, making it a self-contained unit.
________________________________________
How to Use JWT
•	JWT can be sent in multiple ways:
1.	Cookies
2.	Authorization headers (e.g., Authorization: Bearer <token>)
3.	Local storage (in client-side web apps)
________________________________________
JWT Use Case Example
•	Authentication: The server can authenticate a user by verifying the JWT signature and reading the claims directly from the token.
•	Authorization: The server uses the information in the JWT to decide whether the user has the necessary permissions to access specific resources.
________________________________________
Security of JWT
•	The server signs the JWT to ensure its authenticity.
•	When the client sends the JWT in subsequent requests, the server verifies the signature before trusting the contents of the token.
________________________________________
Conclusion
•	JWT is a flexible and efficient solution for authentication and authorization in distributed web applications.
•	It reduces the server’s need to store session data, making it highly scalable for systems like microservices.
•	JWT can be transmitted in various ways (e.g., cookies, headers), offering flexibility in how it is integrated into web apps.

JWT is a secure and compact way to transmit information between parties, mainly used for authorization, not authentication.
________________________________________
📦 JWT Parts (3 Sections)
A JWT is made up of three base64-encoded strings, separated by dots (.):
<Header>.<Payload>.<Signature>
Header : Type of token and the signing algorithm used.
{
  "alg": "HS256",
  "typ": "JWT"
}
Payload Contains the claims: information about the user or token.
•	Common fields:
o	sub – subject (user ID)
o	name – username
o	iat – issued at
o	exp – expiration time
•	⚠️ Do NOT put confidential data (e.g., passwords, SSNs).
•	Example:
{
  "name": "Kaushik",
  "id": "12345",
  "iat": 1714751000
}
Signature Ensures token integrity. Created by signing:
HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
Only the server knows the secret key, so only it can verify the token.
________________________________________
⚙️ How JWT Works
1.	Client logs in, server authenticates using credentials.
2.	Server generates JWT and sends it to client.
3.	Client stores JWT (e.g., in local storage or cookies).
4.	For each request, client sends the JWT in the HTTP header:
Authorization: Bearer <JWT>
5.	Server verifies the token using its secret and grants access if valid.

3.	 What is Single Responsibility Principle in solid principles?

It states  that  “One class should have one and only one responsibility”
Which specifically means - we should write, change, and maintain a class only for one purpose.

Easier to Understand

5.	What is Open/Closed Principle in solid principles?

It states that “Software components should be open for extension, but closed for modification”

The term “Open for extension” means that we can extend and include extra functionalities in our code without altering or affecting our existing implementation.

The term “Closed for modification” means that after we add the extra functionality, we should not modify the existing implementation.

In real world, You must have noticed that you change something to cater a new requirement and some other functionality breaks because of your change. To prevent that we have this principle in hand.

84.	Static in Garbage collection
In Java, the static keyword is used to create class-level variables and methods that are shared across all instances of a class. The static keyword can have an impact on garbage collection (GC) because it affects the lifespan of objects in a class.
1.	Static Variables (Class-level Variables):
o	Memory Management: A static variable belongs to the class itself, not to any specific instance of the class. Static variables are stored in the method area of the Java memory model (which is separate from the heap where instance variables are stored).
o	Lifespan: Static variables live as long as the class itself is loaded into memory. They are not eligible for garbage collection until the class is unloaded (which typically happens when the program terminates or when using custom class loaders).
o	Impact on GC: Static variables do not get garbage collected as long as the class is loaded. This means that objects referenced by static variables can prevent those objects from being garbage collected, even if no instances of the class exist anymore. This can potentially lead to memory leaks if static variables hold references to objects that are no longer needed.
2.	Static Methods:
o	Memory Allocation: Static methods are also stored in the method area (in the class's method table), and they are part of the class itself rather than any object instance.
o	Lifespan: Don’t directly impact garbage collection because methods are not subject to garbage collection. However, if a static method holds references to objects (e.g., via static fields), those objects can be prevented from being garbage collected, as explained for static variables.
3.	Static Classes (Inner Static Classes):
o	A static inner class (a nested class marked with static) does not have a reference to the outer class instance. This means it behaves like a regular class and can be instantiated independently of the outer class.
o	The lifetime of static inner classes is tied to the outer class. If the outer class is still loaded in memory, the static inner class will also be loaded and remain in memory, potentially impacting garbage collection.
85.	Static vs Instance inner class
•	 The inner class does not need access to instance members of the outer class.
•	You want to create instances of the inner class without having an instance of the outer class.
•	You aim to avoid unnecessary memory overhead by not holding an implicit reference to the outer class instance.
•	The inner class is a utility or helper class.
In general, static inner classes are more memory-efficient and flexible when you don't need instance-specific behavior, while instance inner classes are more appropriate when access to the outer class’s instance state is required.

Java memory model(JMM):
Java Memory Model is a set of rules all JVMs have to follow to ensure correct working of our concurrent programs.
JMM specifies set of rules to be followed to ensure visibility of fields amidst reordering of instructions.
Every JVM has to implement these JMM rules.

Out of Order execution : There is a possibility of compiler or JVM to change order of execution of code to boost performance without changing output.
Field visibility:
1.	Registers: small memory portion which is very fast to retrieve and store
2.	L1 cache: Core specific cache
3.	L2 cache: shared cache (Two cores can share one L2 cache)
4.	L3 cache: shared across all cores
5.	RAM: shared across all cores
Higher the level greater size and latency.
Public class VolatileVisiblity{
Int x = 0;
Public void writerThread(){
	x =1 ;
}
Public void readerThread(){
Int r2 = x;
}
}
If we run above program in multi-threaded environment,
•	Initially after initializing x , it will be stored in shared cache
•	Thread-1 executes writerThread() which will increment x value and store it in local cache
•	When Thread-2 executes readerThread() , Still it get x value as 0 only because the  value which updated by thread-1 hasn’t pushed to shared cache.
This is called field visibility problem. We can overcome this by using volatile keyword.
If we specify x as volatile, JVM ensures that whenever any change happened on x it will push the changes to shared cache so if any other thread loads the value it always gets updated value.
  volatile int x = 0;

Spring MVC flow:
1.	HTTP request is received by Dispatcher servlet
2.	As we have lot of controllers in our application, DS internally calls handlerMapper to decide which controller to call for this request.
3.	Handler mapper identifies the controller by it’s name with the help of @RequestMapping (“customers”) annotation and sends details of this controller back to dispatcher Servlet.
4.	Then DS calls the corresponding controller.
5.	Controller is responsible for processing the data. So it will create model data and returns view and model to DS.
6.	DS calls view resolver to decide corresponding view.
7.	ViewResolver identify location of actual view pages and extension and returns to DS
8.	Now DS send content and view to View Component.
9.	View returns HTML page /response to sent back to caller.
10.	DS sends this HTML back to caller.

DBMS:
Entity: Core identities for which the data needs to be stored. (Table) Ex: Book
Relationships: How entities are connected
Attributes:
Data associated with each of the entities. (Columns) Ex: Book: Title, Author and Genre
•	Simple Attribute: Atomic in nature and cannot be divided further. Ex: DOB & ID
•	Composite Attribute: Non atomic in nature and can be divided. Ex: Name (First Name, Middle Name, Last Name)
•	Derived Attributes: Not stored in DB but can be derived from other attributes. Ex: Age
•	Multi Valued Attributes: Can have multiple values. Ex: Email IDs
Keys:
Super Key: An attribute or set of attributes that uniquely identifies a row/’s within as table
•	ISBN & Title can uniquely identify a Book in Library System
Candidate Key: A Super Key where we can still identify row by removing few attributes
•	ISBN can be enough to identify a Book
Primary Key: A Candidate Key selected as the standard to uniquely identify a row. Unselected candidate keys are known as alternative keys
•	ISBN – Primary Key
•	Title – Alternate Key
Foreign Key: Attribute in one table that points to primary key of another table
•	In Transaction Table, ISBN acts as a foreign key as it is a primary key for Book table
Cardinality:
One-to-One: Library Card to Member
•	Each card associated with single member and vice versa
One-to-Many: Member to Transactions
•	Single member can do multiple transactions, but each transaction has only one member in it
Many-to-One: Transaction – to - Book
•	Multiple Transactions can be associated with same book as one person took it today and returns it then other person took it
•	But each transaction record is associated with only one book
Many-to-Many: Book to Category
•	Each book has multiple categories and each category can have multiple books

Normalization:
Technique of organizing the attributes of a DB to reduce redundancy and  remove anomalies
Anomalies:
Student : studentID, name, courseID, courseName, InstructorName
•	Insertion Anomaly: can’t add course information without assigning to students
•	Deletion Anomaly: If we delete record of a student, we might lose course information as well
•	Update Anomaly: If course’s Instructor changes, we need to update it in every row where particular course exist in entire table or else inconsistencies will arise.
We will go through norms convert it progressively before moving ahead
Student: StudentID, StudentName, Courses
First Normal Form (1NF):
•	It contains only atomic values
•	Problem: We have multiple courses for single student which we are breaking atomic property.
•	Solution: We will insert each course separately. If student A takes 2 courses then 2 rows will be created one with each course
Here issue is redundancy as we are repeating student name.
Second Normal Form (2NF):
•	It should be in 1NF
•	All non key (keys which are not primary keys) attributes are fully dependent on primary key.  No partial dependencies
o	Ex: Employee: EmpID, EmpName, ProjectID, ProjectName, DeptName, DeptLocation
o	{EmpID, ProjectID} – Primary key as we can multiple employees in single project. However we have a partial dependency as we can identify name, dept, location with empID itself.
•	Solution: We will divide it into 2 tables
o	Employe : EmpID, EmpName, DeptName, DeptLocation
o	Project: EmpID, ProjectID, ProjectName
Third Normal Form (3NF):
•	It should be in 2NF
•	No Transitive dependencies. DepartmentLocation depends on DepartmentName which in turn depends on EmployeeID
•	Solution: Define separate DeperatmentTable : DeptName, DeptLocation
o	Employe : EmpID, EmpName, DeptName
Boyce-Codd Normal Form (BCNF):
•	It should be in 3NF
•	Course: CourseID,CourseTitle,Department,DeptHead,DeptHeadPhone
o	CourseID -> Tile,Department    By using courseId we can get Title and department
o	Department -> DeptHead,DeptHeadPhone
o	DeptHead -> DeptPhone
•	Solution:
o	Course: CourseId,Title,DepartmentName
o	Department: DepartmentName,DeptHead,DeptHeadPhone
ACID:
Atomicity:
•	Either completes completely or not at all
•	If any part of transaction fails, entire transaction is rolled back
•	If system crashes before committing the transaction, the entire transaction is rolled back
•	If T1 succeeds and T2 fails or vice versa, System should handle this scenario to maintain consistency. Typically rolling back T1 or ensuring both are committed together. Ex: Deposit and Withdraw
Consistency:
•	Transactions should ensure that the database transitions from one consistent state to another.
•	Basically, DB ensures after all transactions, system should remain in consistent state.
Isolation:
•	Transactions should operate independently of each other. Intermediate states should not be visible.
•	If we are in middle of transaction, don’t show the data until transaction is fully completed.
•	Isolation ensures that concurrent transactions do no interfere with each other, maintaining the integrity of the Data base .
Durability:
•	Once a transaction is committed, its changes are permanent and should survive system crashes and failures.
•	So even if system crashes, changes will persist even after system recovers
States of Transaction:
States between Begin and commit.
Active:
•	Ongoing, not yet committed or rolled back
•	Changes are made not yet visible to other transactions
Partially committed:
•	Not Yet committed
•	Waiting for confirmation to permanently save the changes
Committed:
•	Changes are permanent and visible to other transactions
Failed:
•	Cannot procced to commit.
•	If recovery is not possible, it will be rolled back
Aborted:
•	Transaction has been rolled back after a failure
•	Changes are undone.
Indexing:
A technique to speed up the reading of records from a DB table
•	It will improve the efficiency of data retrieval operations at the cost of additional storage and maintenance overhead.
•	Improves query performance by reducing the number of disk reads required to find a record.
•	Index will fetch  records which we are searching up and its near by records and store it RAM for fast retiral.
Types of Index :
Single Column index: Useful when queries frequently filter or sort by this column
Composite Index: Useful when queries filter or sort by multiple columns
Unique Index: Ensures all values in the indexed columns are unique. Ex: Primary Key
Clustered Index:
•	Useful for maintaining sorted order
•	Only one clustered index per table
•	Useful for range queries where data is accessed sequentially
Non-Clustered Index:
•	Separate Structure will be created to points to location of rows
•	Created on columns not included in clustered index
•	Useful for un sorted columns
Indexes are implemented by B-Trees.
B Trees:
A Balanced Tree structured that allows for efficient searching, insertion and deletion.
Properties:
•	All leaves are on same level
•	All Keys are sorted on ascending order
